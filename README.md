# ConceptE: Event Ontology Expansion via LLM-Based Conceptualization

This repository contains the code release for **ConceptE**, a framework for event ontology expansion. ConceptE first enriches event triggers with type-level conceptual abstractions generated by an LLM, then uses the concept-enhanced representations for event clustering, hierarchy linking, and type naming.

## Overview

The full pipeline contains four steps:

1. **Conceptualization**: generate a concept name and concept description for each event trigger.
2. **Event Clustering**: discover unknown event types from concept-enhanced trigger representations.
3. **Hierarchy Linking**: attach discovered clusters to the existing event ontology.
4. **Type Naming**: generate ontology-consistent names for discovered clusters after linking.

## Environment

We recommend Python 3.9+ and PyTorch 2.4.1. Install dependencies with:

```bash
pip install -r requirement.txt
```

If you use an OpenAI-compatible local server such as vLLM, set the API endpoint and key through environment variables:

```bash
export OPENAI_BASE_URL="http://localhost:8000/v1"
export OPENAI_API_KEY="EMPTY"
```

For hosted APIs, replace them with your own endpoint and key. No API token is hard-coded in the released scripts.

## Data Format

The input data should be JSONL or a JSON list. Each record should contain a sentence and event mentions:

```json
{
  "sentence": "The company launched a new product yesterday.",
  "golden-event-mentions": [
    {
      "trigger": {
        "text": "launched",
        "start": 3,
        "end": 4
      }
    }
  ]
}
```

After conceptualization, `get_concept.py` adds trigger-level concept fields:

```json
{
  "trigger": {
    "text": "launched",
    "start": 3,
    "end": 4,
    "trigger_concept_name": "Product-Launch",
    "trigger_concept_description": "An event in which an organization introduces a new product or service."
  }
}
```

The released conceptualization code only uses the **sentence** and **event trigger** as input. It does not generate or require argument-level concepts.

## Running the Pipeline

### 1. Generate Trigger Concepts

```bash
python get_concept.py \
  --input data/ace/test_dev.json \
  --output data/ace/test_dev_concept_Qwen3-32B.json \
  --model Qwen3-32B \
  --openai_api_base "$OPENAI_BASE_URL" \
  --openai_api_key "$OPENAI_API_KEY"
```

For a local vLLM server running Qwen-style chat templates, you can additionally pass:

```bash
--use_vllm_options
```

Useful options:

```text
--start / --end          process a 1-based record range
--max_retries           retry failed or malformed LLM responses
--temperature           decoding temperature, default 0.2
```

### 2. Train Event Clustering

Update the paths in `clustering/run.sh`, then run:

```bash
cd clustering
bash run.sh
```

The script trains the clustering model and saves checkpoints under `clustering/model/`.

### 3. Train Hierarchy Linking

Update `linking/run.sh` so that `--load_checkpoint_path` points to the clustering checkpoint produced in Step 2. Then run:

```bash
cd ../linking
bash run.sh
```

The linking stage predicts the parent path for each discovered cluster. The naming step expects the linking result to be saved as JSON in the following format:

```json
{
  "0": {
    "fathers": ["Attack", "Conflict"],
    "instance": [0, 7, 15, 21]
  },
  "1": {
    "fathers": ["Transport"],
    "instance": [3, 4, 12]
  }
}
```

In the existing linking code, `fathers` are stored in bottom-up order, from the nearest parent to the root. `naming.py` uses this order by default and reverses it internally when constructing the final path.

### 4. Name Discovered Event Types

Run LLM-based type naming after hierarchy linking:

```bash
cd ..
python naming.py \
  --concept_file data/ace/test_dev_concept_Qwen3-32B.json \
  --linking_file outputs/ace_linking.json \
  --known_types data/ace/known_types.txt \
  --output outputs/ace_names.json \
  --method llm \
  --model Qwen3-32B \
  --openai_api_base "$OPENAI_BASE_URL" \
  --openai_api_key "$OPENAI_API_KEY"
```

If you want a deterministic no-LLM naming baseline, use the most frequent concept name in each cluster:

```bash
python naming.py \
  --concept_file data/ace/test_dev_concept_Qwen3-32B.json \
  --linking_file outputs/ace_linking.json \
  --output outputs/ace_names_top_concept.json \
  --method top_concept
```

The naming output contains one item per discovered cluster:

```json
{
  "cluster_id": "0",
  "parent_path": ["Conflict", "Attack"],
  "event_type_name": "Attack",
  "full_path": "Conflict:Attack",
  "num_instances": 4,
  "instance_ids": [0, 7, 15, 21],
  "top_concepts": [
    {
      "name": "Attack",
      "count": 3,
      "description": "A violent or hostile event causing harm or damage."
    }
  ]
}
```

## Notes

- `get_concept.py` and `naming.py` use OpenAI-compatible chat completion APIs.
- API credentials should be passed through environment variables or command-line arguments.
- Conceptualization is trigger-focused: the prompt intentionally excludes argument information.
- `naming.py` is a lightweight post-processing script and does not reload the clustering or linking model.
- The current scripts use gold event triggers to align with prior event ontology expansion settings.
